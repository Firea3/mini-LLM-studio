## 1. Transformer 与自回归语言模型

### 1.1 一句话直觉

> 语言模型就是「给定前文，预测下一个 token」的概率机器；Transformer 用**自注意力**
> 让每个位置直接读取前文所有位置的信息，并用**因果掩码**保证不偷看未来。

### 1.2 核心公式

缩放点积注意力：

$$
\mathrm{Attention}(Q,K,V)=\mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}+M\right)V,
\qquad M_{ij}=\begin{cases}0,& j\le i\\ -\infty,& j>i\end{cases}
$$

多头注意力与残差（pre-LN）：

$$
\mathrm{MultiHead}(X)=\mathrm{Concat}(\mathrm{head}_1,\dots,\mathrm{head}_h)W_O,\qquad
\mathrm{head}_i=\mathrm{Attention}(XW_Q^i,XW_K^i,XW_V^i)
$$

$$
x \leftarrow x + \mathrm{Attn}(\mathrm{LN}(x)),\qquad x \leftarrow x + \mathrm{MLP}(\mathrm{LN}(x))
$$

自回归建模目标（逐 token 交叉熵）与困惑度：

$$
\mathcal{L}_{\mathrm{LM}}(\theta)=-\frac{1}{T}\sum_{t=1}^{T}\log p_\theta(x_t\mid x_{<t}),
\qquad \mathrm{PPL}=\exp(\mathcal{L}_{\mathrm{LM}})
$$

### 1.3 经典出处

* Vaswani et al., *Attention Is All You Need*, NeurIPS 2017 —— Transformer 原始论文。
* Radford et al., *Improving Language Understanding by Generative Pre-Training*, 2018 —— GPT 式 decoder-only 预训练。
* Brown et al., *Language Models are Few-Shot Learners*, NeurIPS 2020 —— GPT-3，规模定律的代表。
* Xiong et al., *On Layer Normalization in the Transformer Architecture*, ICML 2020 —— pre-LN 训练更稳定。

### 1.4 本项目实现位置

| 组件 | 文件 / 符号 | 说明 |
| --- | --- | --- |
| 因果多头注意力 | `minillm/models/tiny_gpt.py` → `CausalSelfAttention.forward` | `qkv` 合并投影；优先用 `F.scaled_dot_product_attention(is_causal=True)`，老版本 torch 回退到手写上三角掩码 softmax（`_HAS_SDPA`） |
| 前馈网络 | `MLP` | `Linear(n_embd, 4*n_embd) → GELU → Linear` |
| 残差块 | `Block` | pre-LN：`x = x + attn(ln_1(x))`、`x = x + mlp(ln_2(x))` |
| 主干 | `TinyGPT.forward` / `_encode` / `forward_hidden` | `_encode` 复用给 LM 头、奖励头、价值头；输出头与 embedding 共享权重（`tie_weights`） |
| 生成 | `TinyGPT.generate` | 温度采样 / 贪心（`temperature<=0`）/ top-k 截断 / EOS 后填 pad；上下文超 `block_size` 时截断左侧 |
| 参数量 | `TinyGPT.num_parameters` | 默认配置 392,352（含共享 embedding 只计一次） |
| 超参定义 | `minillm/config.py` → `ModelConfig` | `n_layer=3, n_head=4, n_embd=96, block_size=128, dropout=0.1, tie_weights=True, init_std=0.02` |

### 1.5 关键超参与工程取舍

* **为什么是 decoder-only**：项目要同时覆盖「语言建模」和「策略网络」两种角色，decoder-only 的
  `forward_hidden` 可以直接接奖励头/价值头，结构复用最彻底。
* **为什么用可学习位置编码**：序列长度上限只有 `block_size=128`，可学习 `wpe` 实现简单、
  参数只有 `128×96=12,288`，无需引入 RoPE 实现与调试成本。
* **pre-LN 而非 post-LN**：小模型 + AdamW + 300 步训练，pre-LN 不需要 learning-rate warmup
  之外的额外技巧即可稳定收敛。
* **融合 SDPA**：CPU 上同样走 PyTorch 优化内核；保留手写掩码分支保证可移植性。
* **权重共享（tie_weights）**：默认配置下 embedding 占 `474×96=45,504` 参数，
  共享输出头可省掉同样大小的一份参数，并改善小语料泛化。
* **GELU 而非 ReLU**：与 GPT 系列一致，曲线更平滑，小模型上收敛略稳。

## 2. 字符级 Tokenizer（CharTokenizer）

### 2.1 一句话直觉

> 中文没有天然空格分词，字符级分词把「每个汉字/每个字母/每个符号」直接映射为一个 id：
> 无需训练 BPE、没有 OOV 灾难，代价是序列变长、单 token 语义密度低。

### 2.2 核心公式

字符级编码映射（`c` 为字符，`V_c` 为字符表）：

$$
\mathrm{encode}(s)=[\,\mathrm{BOS}\,]\;\Vert\;\big[\,\mathrm{id}(c)\ \big|\ c\in s\,\big]\;\Vert\;[\,\mathrm{EOS}\,],
\qquad
\mathrm{id}(c)=\begin{cases}4+i,& c=V_c[i]\\ 3,&\text{otherwise}\end{cases}
$$

序列长度与压缩比（项目语料实测）：

$$
|s|_{\text{tokens}}=|s|_{\text{chars}}+2,\qquad
\text{vocab\_size}=4+|V_c|
$$

### 2.3 经典出处

* Sennrich et al., *Neural Machine Translation of Rare Words with Subword Units*, ACL 2016 —— BPE 子词。
* Kudo & Richardson, *SentencePiece*, EMNLP 2018 —— 语言无关子词方案。
* 本项目取舍参考：中文场景下「字符级」≈ 一种极端的、零训练成本的子词方案。

### 2.4 本项目实现位置

| 能力 | 符号 | 说明 |
| --- | --- | --- |
| 特殊 token 契约 | `SPECIAL_TOKENS` / `SPECIAL_IDS` | `<pad>=0, <bos>=1, <eos>=2, <unk>=3`，全项目共享 |
| 构建词表 | `CharTokenizer.build` | 统计字符频次，按 `(-freq, char)` 排序，保证同语料结果完全一致 |
| 编解码 | `CharTokenizer.encode` / `decode` | `decode` 跳过 id<4 的特殊 token |
| 持久化 | `to_dict` / `from_dict` / `save` / `load` | 带 `version=1`，加载时校验特殊 token id 契约 |
| 词表规模 | `vocab_size` | 当前 `artifacts/tokenizer.json` 读出 474（即 470 个字符 + 4 个特殊 token） |
| 使用点 | `minillm/train/pretrain.py` → `run_pretrain` | 词表来自「`corpus.txt` + `sft.jsonl` 全文」，训练序列只来自 `corpus.txt`，避免 SFT 阶段 OOV |

### 2.5 关键超参与工程取舍

* `min_freq=1, max_vocab=3000`：语料只有 12,483 字符（`data/processed/stats.json`），
  实际字符表 470 个，远小于上限，因此不会发生裁剪。
* **词表来源包含 SFT 文本**：这是「预训练词表覆盖下游字符」的常见做法；否则 SFT 中出现的
  少量字符会全部变成 `<unk>`，监督信号被稀释。
* **检查点与分词器强绑定**：所有训练器/服务在加载时都会校验 `model.cfg.vocab_size == tokenizer.vocab_size`，
  不一致直接报错（`sft.py`、`reward.py`、`ppo.py` 均有该校验），避免「用旧词表解码新模型」的静默错误。
* **取舍代价**：字符级序列比 BPE 长 2~4 倍，`block_size=128` 在长文本上会截断；
  同时模型需要更多步数才能学到「词」的组合结构，这是本项目 PPL 偏高（相对于大模型）的主因之一。

## 3. LoRA（Low-Rank Adaptation）

### 3.1 一句话直觉

> 大模型微调不必改全部权重：冻结原矩阵 `W`，只在旁边学一个很瘦的「低秩补丁」`BA`，
> 参数量从百万级降到万级，训练完还能合并回原权重、零推理开销。

### 3.2 核心公式

对冻结的线性层 `y = xW^{\top}`，LoRA 前向为：

$$
y = xW^{\top} + \frac{\alpha}{r}\,x A^{\top}B^{\top},
\qquad A\in\mathbb{R}^{r\times d_{\text{in}}},\ B\in\mathbb{R}^{d_{\text{out}}\times r}
$$

初始化 `B=0`，因此训练起点 `ΔW=BA=0`，与原模型完全等价。可训练参数量：

$$
\#\text{params}_{\text{LoRA}} = r\,(d_{\text{in}}+d_{\text{out}})
$$

合并（推理期）：

$$
W' = W + \frac{\alpha}{r}BA
$$

### 3.3 经典出处

* Hu et al., *LoRA: Low-Rank Adaptation of Large Language Models*, ICLR 2022 —— 原始论文。
* Aghajanyan et al., *Intrinsic Dimensionality Explains the Effectiveness of Language Model Fine-Tuning*, ACL 2021 —— 低秩假设的理论动机。

### 3.4 本项目实现位置

| 能力 | 符号 | 说明 |
| --- | --- | --- |
| 包装线性层 | `minillm/models/lora.py` → `LoRALinear` | 冻结 `base`，新增 `lora_A`（kaiming 初始化）、`lora_B`（零初始化） |
| 注入 | `apply_lora(model, r=8, alpha=16.0, dropout=0.0, exclude=("lm_head",))` | 先冻结全部参数，再递归替换 `nn.Linear`，最后解冻 LoRA 参数 |
| 参数列表 | `lora_parameters` | 供优化器只更新 LoRA 参数 |
| 合并 | `merge_lora` / `LoRALinear.merge` | 把 `ΔW` 加回 `base.weight` 并还原为普通 `nn.Linear` |
| 训练入口 | `minillm/train/sft.py` → `run_sft` | `cfg.sft.use_lora=True` 时启用，训练结束 `merge_lora` 后再保存为普通 `kind="gpt"` 检查点 |
| 超参 | `minillm/config.py` → `SFTConfig` | `use_lora=False`（默认）、`lora_r=8`、`lora_alpha=16.0`、`lora_dropout=0.05` |

### 3.5 关键超参与工程取舍

* **默认关闭**：本项目模型只有 39 万参数，全参微调已经不贵；LoRA 的价值在于演示「参数高效微调」
  的工程实现与合并正确性，而不是省显存。开启后按默认配置实测可训练参数 **36,864**。
* **为什么排除 `lm_head`**：`tie_weights=True` 时 `lm_head.weight` 与 `wte.weight` 是同一份
  `Parameter`，若给 `lm_head` 注入 LoRA，`merge` 会连带修改 embedding，输出不再等价。
  代码在 `apply_lora` 的 `exclude` 参数与 docstring 中明确记录了这个坑。
* **`r=8, alpha=16`**：`scaling = alpha/r = 2.0`，是 LoRA 论文中常用的比例；中文小语料下
  `r` 太大容易过拟合，8 足够。
* **合并后保存**：服务端只认 `kind ∈ {gpt, policy, reward}`，不需要识别 LoRA 结构，
  降低了推理侧复杂度。

## 4. Bradley-Terry 奖励模型

### 4.1 一句话直觉

> 人类没法直接标「这个回答值 3.7 分」，但可以稳定回答「A 和 B 谁更好」。
> Bradley-Terry 模型把成对偏好转成概率，奖励模型学一个标量 `r(x)`，让 chosen 的分数系统性高于 rejected。

### 4.2 核心公式

成对偏好概率：

$$
P(y_{\text{chosen}}\succ y_{\text{rejected}}\mid x)
=\sigma\big(r_\phi(x,y_{\text{chosen}})-r_\phi(x,y_{\text{rejected}})\big)
$$

负对数似然损失（带可选 margin）：

$$
\mathcal{L}_{\mathrm{BT}}(\phi)
=-\mathbb{E}_{(x,y_c,y_r)\sim\mathcal{D}}
\log\sigma\big(r_\phi(x,y_c)-r_\phi(x,y_r)-m\big)
$$

评估指标（成对准确率与平均间隔）：

$$
\mathrm{Acc}=\mathbb{E}\big[\mathbb{1}(r_c>r_r)\big],\qquad
\mathrm{Margin}=\mathbb{E}[r_c-r_r]
$$

### 4.3 经典出处

* Bradley & Terry, *Rank Analysis of Incomplete Block Designs: I. The Method of Paired Comparisons*, Biometrika 1952。
* Christiano et al., *Deep Reinforcement Learning from Human Preferences*, NeurIPS 2017 —— 偏好学习 + RL 的奠基工作。
* Ouyang et al., *Training Language Models to Follow Instructions with Human Feedback*, NeurIPS 2022（InstructGPT）—— RLHF 三阶段范式。

### 4.4 本项目实现位置

| 能力 | 符号 | 说明 |
| --- | --- | --- |
| 成对损失 | `minillm/models/reward_model.py` → `pairwise_loss` | `-logsigmoid(r_c - r_r - margin).mean()` |
| 奖励模型 | `RewardModel` | `TinyGPT.forward_hidden` → 取**最后一个有效 token** 的 hidden → `reward_head: Linear(n_embd, 1)` |
| mask 处理 | `RewardModel.forward` | `lengths = mask.sum(dim=1) - 1` 定位最后有效位置，padding 不参与 |
| 训练流程 | `minillm/train/reward.py` → `run_reward` | backbone 从 `artifacts/sft/model.pt` 初始化；`encode_preference` 超长时保留 BOS + 尾部；**每个 epoch 在验证集评估，按 `(val_acc, val_margin)` 字典序保存最优权重**（小数据下防止过拟合） |
| 数据增强（trainer 内） | `run_reward` | 从 `sft.jsonl` 派生「正确回答 vs 随机另一条回答」120 条同领域难负例，训练对 **64 → 184**；**只读数据文件、不改 `data/processed`；验证集仍只用 `pref.jsonl` 的 val 划分（16 对），指标不被污染** |
| 验证指标 | `_evaluate_reward` | 返回 `(val_acc, val_margin)`，写入 `reports/lm_metrics.json` 的 `reward` 节（含 `best_epoch`、`data_aug`、`augmented_pairs`、`train_pairs`） |
| 超参 | `minillm/config.py` → `RewardConfig` | `epochs=6, batch_size=8, lr=1e-3, val_ratio=0.2, margin=0.0, seed=0` |

### 4.5 关键超参与工程取舍

* **只取最后 token 表征**：小模型 + 短回答，最后位置已经通过因果注意力聚合了整段信息；
  比 pooling 全序列更简单，也与 PPO 里「序列奖励加在最后一个 token」的设计对齐。
* **奖励头小初始化**：`std=init_std=0.02`，避免初始奖励尺度失控导致 PPO 早期 KL 爆炸。
* **按验证集选最优 epoch**：训练偏好对很少 + 392K 参数极易过拟合，
  因此 `run_reward` 每 epoch 评估验证集并按 `(val_acc, val_margin)` 保留最优权重。
  实测：**无增强基线 val_acc=0.625（best_epoch=4）→ 加入 120 条 SFT 派生难负例后
  val_acc=0.8125（best_epoch=6）、val_margin 2.317**；最终 reward 检查点保存的是增强后的 `best_epoch=6` 权重。
* **数据增强的边界**：只从 `sft.jsonl` 派生（正确回答 vs 随机另一条回答），
  验证集仍只用 `pref.jsonl` 的 val 划分，所以 0.8125 不是「用增强数据自评」的虚高数字。
* **偏好数据本身的局限**：`scripts/build_data.py` 的 rejected 来自「其他文档的答案」（答非所问），
  所以奖励模型主要学到「答案是否谈到该主题」；即使增强后，它对**数字是否正确仍不敏感**
  （实测 5000000 元的错误答案奖励高于 500000 元），这是 PPO 提升幅度有限的原因之一
  （详见《技术报告》§6.2、§7.3）。
* **margin=0**：不额外要求奖励间隔，先保证排序正确；margin 作为可配置项保留。

## 5. PPO / GAE / token 级 KL（RLHF）

### 5.1 一句话直觉

> SFT 教会模型「怎么答」，奖励模型告诉它「哪种答法更好」，PPO 则在「多拿奖励」和
> 「别离 SFT 太远」之间做带信任域的权衡：用 clip 限制策略更新幅度，用逐 token KL 惩罚防止语言跑偏。

### 5.2 核心公式

**策略比率与 clipped surrogate**：

$$
\rho_t(\theta)=\frac{\pi_\theta(a_t\mid s_t)}{\pi_{\theta_{\text{old}}}(a_t\mid s_t)},
\qquad
L^{\mathrm{CLIP}}(\theta)=\mathbb{E}_t\Big[\min\big(\rho_t A_t,\ \mathrm{clip}(\rho_t,1-\epsilon,1+\epsilon)A_t\big)\Big]
$$

实际优化目标（带熵正则，注意符号：梯度上升 → 最小化负目标）：

$$
\mathcal{L}(\theta)=-\Big[L^{\mathrm{CLIP}}(\theta)+\beta_H\,\mathcal{H}\big[\pi_\theta(\cdot\mid s_t)\big]\Big]
$$

**GAE（广义优势估计）**：

$$
\delta_t = r_t + \gamma V_\phi(s_{t+1}) - V_\phi(s_t),
\qquad
\hat{A}_t = \delta_t + \gamma\lambda\,\hat{A}_{t+1},
\qquad
\hat{R}_t = \hat{A}_t + V_\phi(s_t)
$$

**token 级 KL 惩罚奖励**（把 KL 直接折进每步奖励，而不是仅在 loss 里加正则）：

$$
r_t = -\beta_{\mathrm{KL}}\big(\log\pi_\theta(a_t\mid s_t)-\log\pi_{\text{ref}}(a_t\mid s_t)\big)
\;+\;\mathbb{1}[t=T]\cdot r_\phi(x,y)
$$

价值网络回归目标：

$$
\mathcal{L}_V(\phi)=\mathbb{E}_t\big[(V_\phi(s_t)-\hat{R}_t)^2\big]
$$

### 5.3 经典出处

* Schulman et al., *Proximal Policy Optimization Algorithms*, arXiv 2017 —— PPO / clipped surrogate。
* Schulman et al., *High-Dimensional Continuous Control Using Generalized Advantage Estimation*, ICLR 2016 —— GAE。
* Stiennon et al., *Learning to Summarize from Human Feedback*, NeurIPS 2020 —— PPO + 奖励模型的经典配方。
* Ouyang et al., *Training Language Models to Follow Instructions with Human Feedback*, NeurIPS 2022 —— token 级 KL 惩罚的工程实践。
* Jaques et al., *Way Off-Policy Batch Deep Reinforcement Learning of Implicit Human Preferences in Dialog*, 2019 —— KL 控制用于对话生成。

### 5.4 本项目实现位置

| 组件 | 符号 | 说明 |
| --- | --- | --- |
| rollout 采样 | `minillm/train/ppo.py` → `_sample_sequences` | 每步把所有序列右填充成矩形 batch；因果注意力保证右侧 padding 不影响真实最后位置 logits；EOS 后填 pad，最后裁剪回 EOS |
| 动作张量整理 | `_action_layout` | 返回 `(input_ids [B,L-1], actions [B,T], positions [B,T], mask [B,T])`；`positions = prompt_len + t - 1` 是产生该 action 的 logits 下标 |
| 动作 logprob / 熵 | `_action_logprobs` | `log_softmax` 后按 `positions*V + actions` 展平 gather；同时算熵 |
| 状态价值 | `ValueModel` + `_values_at` | TinyGPT backbone + 标量头，输出每个位置的 `V(s_t)`，padding 位置置 0 |
| GAE | `_compute_gae` | 反向递推，`next_value` 从 0 开始（终止状态价值为 0）；**`δ_t` 与 `A_t` 都在 padding 位置乘 mask 清零**，避免噪声沿 `γλ` 反向泄漏（本项目第一版曾因此退化） |
| 旧策略/参考策略 | `run_ppo` 内 `old_logp` / `ref_logp` | 参考策略是 `copy.deepcopy(policy)` 后冻结的 SFT 策略；奖励模型同样冻结 |
| token 级 KL 奖励 | `run_ppo` | `token_kl = old_logp - ref_logp`，`rewards = -kl_coef * token_kl * mask`（padding 奖励置 0），并在每个序列最后一个有效 token 上叠加奖励模型的终局分 |
| 优势归一化 | `run_ppo` | 只用有效 action 的均值/标准差归一化，按 mask 屏蔽 padding |
| 策略更新 | `run_ppo` | `ratio = exp((new_logp-old_logp).clamp(-20,20))`，`surr1/surr2` 取 min，减 `entropy_coef * H`，`clip_grad_norm_=1.0` |
| 价值更新 | `run_ppo` | 独立优化器 `value_lr=5e-4`，回归 `returns` |
| 评估 prompt | `run_ppo` | 用 `random.Random(seed+7)` 从全部 prompt 中抽 8 条（与训练随机流隔离、覆盖不同主题），before/after 同口径 |
| 评估 | `_evaluate_policy` | 在固定的 8 条 eval prompt 上 **greedy** 生成，用奖励模型打分，得到 `mean_reward_before/after` 与样本 |
| 最优检查点 | `run_ppo` 主循环 | 每 `max(1, max_steps//10)` 步用**同一 greedy 口径**评估，保留评估奖励最高的策略快照；**SFT 初始策略（step 0）也是候选**，结束时恢复最优权重并报告 `best_step` / `mean_reward_after`，同时用 `mean_reward_final` 透明记录最后一步的评估奖励 |
| 产物 | `run_ppo` 尾部 | `artifacts/ppo/model.pt`（`kind="policy"`）、`reports/lm_metrics.json` 的 `ppo` 节（含 `best_step`、`mean_reward_final`）、`reports/ppo_samples.json`（含 `samples` 与 `baseline_samples`） |
| 超参 | `minillm/config.py` → `PPOConfig` | 见下表 |

| --- | --- | --- |

| `batch_prompts` | 8 | 每轮 rollout 的 prompt 数 |

| `seed` | 0 | 全局可复现 |

### 5.5 工程取舍（PPO 为什么这么写）

* **token 级 KL 而不是 sequence 级 KL**：逐 token 反馈更密集，小 batch 下也能稳定约束；
  与 InstructGPT 的做法一致。代价是 `ref_logp` 需要额外一次前向（本项目每轮 3 次前向：policy/ref/value）。
* **奖励加在最后一个有效 action 上**：奖励模型只对完整序列打一个标量，这是最常见、最省事的
  终端奖励设计；GAE 会把它沿轨迹回传。
* **参考策略冻结、奖励模型冻结**：避免 reward hacking 与 KL 计算漂移。
* **GAE 的 mask 必须贯穿递推**：变长序列里 padding 位置的 `r_t`/`V_t` 没有意义，
  旧实现只在最后输出乘 mask，导致噪声沿 `γλ` 反向污染有效 token 的优势，
  实测会把 PPO 从 −0.86 训到 −1.17。修复方式是 `δ_t` 与 `A_t` 都乘 mask 清零
  （`minillm/train/ppo.py` → `_compute_gae`），这是本项目的关键修复（详见《技术报告》§7.1）。
* **不做 reward normalization**：只做 advantage 归一化，保持实现简洁；奖励模型本身输出尺度
  已被小初始化约束（见 §4.5）。
* **评估用 greedy + 固定抽样**：用 `seed+7` 从全部 prompt 中抽 8 条、greedy 解码，
  保证 before/after 同口径、可复现，也避免只抽到同一主题（本项目早期只取文件前 8 条，
  全是「食堂」类问题，放大了字符级模型在数字上的循环）。
* **按评估奖励保留最优检查点（早停思想）**：小数据 RLHF 中奖励模型的噪声可能让策略越训越差，
  所以主循环周期性（默认每 `max_steps//10` 步）用**与 before/after 相同的 greedy 口径**评估，
  保留最优快照，**SFT 初始策略（step 0）也是候选**。因此最终交付的策略在评估口径上不会差于 SFT；
  同时用 `mean_reward_final` 记录「不挑选、最后一步」的奖励，避免「只报最优」的信息损失。
* **baseline 样本同时落盘**：`reports/ppo_samples.json` 里同时保存 `samples`（PPO greedy）与
  `baseline_samples`（SFT greedy），方便逐条对比「是否真的变好」，而不是只看一个平均分。
* **如实记录**：`minillm/train/ppo.py` 模块 docstring 明确写了「若 PPO 效果下降也照实记录」；
  `best_step=0` 时同样照实报告「PPO 未找到优于 SFT 的策略」。指标文件不做过拟合式挑选。

## 6. DQN / Double DQN / 经验回放 / 目标网络

### 6.1 一句话直觉

> Q-Learning 学会「在状态 s 做动作 a 未来能拿多少回报」；DQN 用神经网络近似 Q 表，
> 再用经验回放打破样本相关性、用目标网络稳住 TD 目标、用 Double DQN 抑制 `max` 带来的系统性高估。

### 6.2 核心公式

**TD 目标（原始 DQN）**：

$$
y_t = r_t + \gamma (1-d_t)\max_{a'} Q_{\bar\theta}(s_{t+1},a')
$$

**Double DQN 目标（本项目采用）**：在线网络选动作、目标网络估值：

$$
y_t = r_t + \gamma (1-d_t)\, Q_{\bar\theta}\Big(s_{t+1},\ \arg\max_{a'}Q_\theta(s_{t+1},a')\Big)
$$

**Huber 损失（smooth L1）**：

$$
\mathcal{L}(\theta)=\mathbb{E}\Big[\mathrm{Huber}_\delta\big(Q_\theta(s_t,a_t)-y_t\big)\Big]
$$

**epsilon-greedy 衰减**：

$$
\epsilon_{k+1}=\max(\epsilon_{\min},\ \epsilon_k\cdot\lambda_\epsilon),
\qquad \epsilon_0=1.0,\ \epsilon_{\min}=0.05,\ \lambda_\epsilon=0.985
$$

### 6.3 经典出处

* Watkins & Dayan, *Q-learning*, Machine Learning 1992 —— Q-Learning 原始论文。
* Mnih et al., *Human-level Control through Deep Reinforcement Learning*, Nature 2015 —— DQN（经验回放 + 目标网络）。
* van Hasselt et al., *Deep Reinforcement Learning with Double Q-Learning*, AAAI 2016 —— Double DQN 抑制高估。
* Sutton & Barto, *Reinforcement Learning: An Introduction* (2nd ed.) —— 值函数与 TD 的系统教材。

### 6.5 工程取舍

* **确定性环境**：没有随机转移，`seed` 只保留接口；好处是「同一策略同一轨迹」，
  测试与验收不需要统计检验，坏处是训练曲线平滑得「太漂亮」，不能代表真实随机环境。
* **one-hot 观测**：把 DQN 退化成可泛化的 Q 表，便于人工核对学到的策略是否合理。
* **Double DQN 而非原版**：原版 `max` 目标在早期容易高估，本项目实测改用 Double DQN 后
  训练末期不发生策略回退（该问题的排查过程见《设计流程思考》第 8 节）。
* **保存「最优」而非「最后」模型**：以 `(成功率, 平均回报)` 字典序选优，避免训练后期偶发崩溃覆盖好模型。

## 7. BM25 检索

### 7.1 一句话直觉

> 一句话里出现查询词越多、这些词越稀有，这句话就越相关；再用文档长度做归一化，
> 避免长文档靠「词多」占便宜。BM25 是关键词检索几十年沉淀下来的强基线。

### 7.2 核心公式

$$
\mathrm{BM25}(D,Q)=\sum_{t\in Q}\mathrm{IDF}(t)\cdot
\frac{f(t,D)\,(k_1+1)}{f(t,D)+k_1\big(1-b+b\cdot\frac{|D|}{\mathrm{avgdl}}\big)}
$$

本项目采用对低频词更友好的 IDF 变体（保证非负）：

$$
\mathrm{IDF}(t)=\ln\!\left(1+\frac{N-\mathrm{df}(t)+0.5}{\mathrm{df}(t)+0.5}\right)
$$

其中 `f(t,D)` 为词频、`|D|` 为文档长度（token 数）、`avgdl` 为平均长度、
`k1=1.5` 控制词频饱和、`b=0.75` 控制长度归一化强度。

### 7.3 经典出处

* Robertson & Zaragoza, *The Probabilistic Relevance Framework: BM25 and Beyond*, Foundations and Trends in IR, 2009 —— BM25 系统总结。
* Robertson et al., *Okapi at TREC-3*, TREC 1994 —— Okapi BM25 原始系统描述。
* Manning et al., *Introduction to Information Retrieval*, CUP 2008 —— 第 11 章概率检索模型。

### 7.4 本项目实现位置

| 组件 | 符号 | 说明 |
| --- | --- | --- |
| 中英混合分词 | `minillm/rag/retriever.py` → `tokenize` | 连续汉字段切 **字符 unigram + 相邻 bigram**；英文/数字整词小写；过滤空白标点 |
| 策略接口 | `BaseRetriever` | `index(docs)` / `search(query, top_k)` |
| 检索器 | `BM25Retriever` | 预计算 `tf/df/idf/avgdl`；查询词去重避免分数翻倍；同分按原始顺序保证稳定 |
| 摘要 | `BM25Retriever._snippet` | 在命中词附近截取不超过 `snippet_chars=120` 的窗口 |
| 工厂 + 注册表 | `RETRIEVER_REGISTRY` / `build_retriever` | `@RETRIEVER_REGISTRY.register("bm25")`，便于换成向量检索 |
| 配置 | `minillm/config.py` → `RAGConfig` | `top_k=3, bm25_k1=1.5, bm25_b=0.75, min_score=0.0, max_context_chars=800, snippet_chars=120` |
| 语料 | `minillm/rag/docs.py` → `load_documents` | FAQ 50 条（一条一个 chunk，`doc_id` 为父文档、`chunk_id` 为 `faq.id`）+ 知识库 10 篇（一篇一个 chunk），共 60 个 chunk |

### 7.5 关键超参与工程取舍

* **中文 unigram + bigram**：不引入分词模型即可兼顾召回（单字）与精度（bigram 让「图书馆」
  这类术语有更高权重），实现不到 20 行。
* **纯 Python 实现**：零第三方依赖，`index` + 60 篇文档的检索在毫秒级，CPU 完全够用。
* **IDF 使用 `ln(1 + ...)` 变体**：经典 BM25 的 IDF 在「词出现在超过一半文档」时可能为负，
  小语料下会让分数不可解释；该变体恒为正，且仍保留稀有词更高的权重。
* **`min_score=0.0` 过滤 0 分**：避免完全无关的文档进入上下文，减少生成器被噪声误导。
* **易/难两组评估**：`evaluate_rag` 既接受 `eval_qa.jsonl` 也可以直接吃内置的
  `HARD_EVAL_QUERIES`（10 条人工语义改写，刻意避开原文档高频词）。实测简单集
  recall@1=1.0，难例集 recall@1=0.70、recall@3=0.90、MRR=0.80 ——
  **用一组对照量化词法检索的上限**，详见《技术报告》§6.3。
* **局限**：BM25 是**词法匹配**，同义改写（如「闭馆时间」vs「几点关门」）若共享字符很少
  就会漏召回；这也是《技术报告》里分析 recall 上限的主要依据。

## 8. RAG（检索增强生成）

### 8.1 一句话直觉

> 让模型「开卷考试」：先从知识库检索相关片段，再把「资料 + 问题」一起喂给生成器，
> 答案里标注引用编号，从而降低幻觉、让结论可溯源。

### 8.2 核心公式

生成式 RAG 的概率分解（Lewis et al. 2020）：

$$
p(y\mid x)\approx\sum_{z\in\mathrm{top}\text{-}k(x)}p_\eta(z\mid x)\,p_\theta(y\mid x,z)
$$

检索质量指标：

$$
\mathrm{Recall@}k=\frac{1}{|Q|}\sum_{q\in Q}\mathbb{1}\big[\mathrm{gold}(q)\in\mathrm{top}_k(q)\big],
\qquad
\mathrm{MRR}=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{\mathrm{rank}_q}
$$

本项目实际评估的是**检索阶段**（recall@1 / recall@3 / MRR），生成质量用人工/样例检查。

### 8.3 经典出处

* Lewis et al., *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*, NeurIPS 2020 —— RAG 原始论文。
* Karpukhin et al., *Dense Passage Retrieval for Open-Domain Question Answering*, EMNLP 2020 —— 向量检索（DPR）基线。
* Gao et al., *Retrieval-Augmented Generation for Large Language Models: A Survey*, arXiv 2023 —— RAG 综述。

### 8.4 本项目实现位置

| 组件 | 符号 | 说明 |
| --- | --- | --- |
| 文档加载 | `minillm/rag/docs.py` → `load_documents` | FAQ 正文 = 问题 + 答案；KB 正文 = 标题 + 摘要；缺字段记录 warning 并跳过 |
| 上下文拼接 | `minillm/rag/pipeline.py` → `RAGPipeline.build_context` | 每条命中带 `[编号] 标题：正文`，总长受 `max_context_chars=800` 约束 |

### 8.5 关键超参与工程取舍

* **`top_k=3`**：上下文窗口只有 800 字符，3 条片段已经接近预算上限；再多会挤掉问题本身。
* **抽取式回退不是「假装生成」**：它在 `GenerationResult.source` 与 `RAGAnswer.source` 中
  **显式标注来源**——没有模型时是 `extractive`；有模型但被守卫拦截时是 `extractive_fallback`；
  通过校验时是 `model`。服务端 `/health` 的 `generator` 字段也会暴露
  `model_guarded` / `model` / `extractive` / `unavailable`，调用方能区分
  「模型生成」「守卫回退」「纯抽取」，这是本项目「可解释降级」的核心设计。
* **引用溯源到父文档**：`doc_id` 是评估 gold 的口径，`chunk_id` 用于定位具体 FAQ，
  二者分开存储（`minillm/types.py` → `Document`）。
* **不引入向量库**：60 个 chunk 的规模下，BM25 的召回已经足够演示 RAG 链路，
  且避免 embedding 模型下载与依赖膨胀（选型对比见《设计流程思考》§3）。
* **易/难双评估集**：除 `data/processed/eval_qa.jsonl`（30 条模板改写）外，
  `HARD_EVAL_QUERIES` 内置 10 条人工语义改写难例（gold 为 eval 文档），
  两组指标分别写入 `reports/app_metrics.json` 的 `rag` 与 `rag_hard`。
  实测简单集 recall@1=1.0，难例集 recall@1=0.70 / recall@3=0.90 / MRR=0.80 ——
  **主动暴露弱项，而不是只报告好看的数字**。

### 8.6 生成质量守卫：为什么需要、怎么实现、边界在哪

**为什么需要**：本项目 TinyGPT 只有 392K 参数 + 字符级词表，自由生成时有三类高发问题：
① **幻觉**（答案与检索资料几乎无字符重合，或编造「营业到 217:30」「电话 8260 9999」）；
② **重复崩溃**（同一字/短语循环，如「7:0-9:0-9:0」）；
③ **碎片拼接/语法碎片**（如「图书馆 7 7 7 7 3:0。」「第一次0。」）。RAG 对事实性要求高，
把这类答案直接给用户会误导人。

**实现**（`minillm/rag/pipeline.py` → `GuardedGenerator`）：
主生成器（`TinyGPTGenerator`）输出后，按以下 **9 条规则**逐条校验（按代码检查顺序），
**任一不满足或生成异常**就改用 `ExtractiveGenerator` 的答案，并标记
`source="extractive_fallback"`；全部通过则透传 `source="model"`。

| # | 规则函数 | 阈值/逻辑 | 拦截的问题 |
| --- | --- | --- | --- |
| 1 | `is_placeholder_text` | 命中 `PLACEHOLDER_MARKERS`（「当前为抽取式回退」「占位」等） | 占位/回退提示被当答案 |
| 2 | `has_valid_length` | 有效字符 ≥ `GUARD_MIN_CHARS=4` | 「有。」这类过短输出 |
| 3 | `context_coverage` | 对整段 context 的字符覆盖率 ≥ `GUARD_MIN_CONTEXT_COVERAGE=0.6` | 与资料无关的幻觉 |
| 4 | `max_chunk_coverage` | 对**单个检索片段**的覆盖率 ≥ `GUARD_MIN_CHUNK_COVERAGE=0.75` | 多片段碎片拼接 |
| 5 | `has_ungrounded_numbers` | 答案中数字 token（≥2 位）必须能在 context 中找到 | 编造时间/电话/金额 |
| 6 | `has_excessive_repetition` | 连续相同字符 ≤ 4，且重复 4-gram 比例 < 0.5 | 字符级模型复读 |
| 7 | `missing_required_quantity` | 问题命中「几点/多少/电话/金额/额度…」时，答案必须含至少一个数字 | 「字字有出处但答非所问」 |
| 8 | `missing_question_anchor` | 答案与问题至少共享一个 2-gram | 「第一次0。」式语法碎片 |
| 9 | `max_chunk_similarity` | 答案与最相似片段的最长连续匹配 ≥ 答案长度 75% | 「图书馆 7 7 7 7 3:0。」式碎片；**最后检查**，前 8 条先报更具体原因 |

**实测结论（重要，如实记录）**：在 392K 字符级小模型 + 当前训练数据下，
抽检 **12 个常见问题**（图书馆闭馆时间、食堂时间、报修电话、奖学金金额、校医院、校园网等），
**12/12 全部触发守卫回退**，RAG 输出均为正确的抽取式答案并带 citations。
单一案例：问「图书馆周五几点闭馆？」模型输出被 `missing_quantity` 拦截；
问「第一食堂早餐几点开始？」被 `ungrounded_number` 拦截。这是**预期取舍**：
「RAG 对事实性要求高，宁可用检索原文，也不展示不可信生成」；
模型生成能力通过 `/v1/generate` 单独演示，训练/对齐效果通过 `reports/*.json` 与
`reports/ppo_samples.json` 展示。

**边界（必须诚实说明）**：

* 守卫是**词法级/规则级兜底**：它能拦住「无来源、编数字、复读、过短、缺数字、碎片拼接、
  语法碎片」，但**拦不住语义层面的答非所问**——例如问题问「为什么」，
  答案给了一个相关但不解释原因的事实句，规则可能放过。真正解决要靠更强的模型或答案级评估（NLI/人工）。
* 守卫**不提升模型能力**，只是把不可信输出挡在用户面前；`source` 字段保证可解释。
* `/v1/generate` 是「裸模型生成演示」，**不经过守卫**；只有 RAG 问答（`/v1/rag/answer`、
  `/v1/chat` 的 rag 路径）才经过守卫。这是刻意的：演示模型能力与保证答案可靠是两件事。

## 9. ReAct Agent 与工具调用

### 9.1 一句话直觉

> 让模型「边想边做」：每一步先产出思考（Thought）和动作（Action），执行工具得到观察
>（Observation），再决定下一步；直到给出最终答案（Final Answer）。比一次性生成更可靠，
> 因为外部工具把「算数、查资料」这类不确定任务外包给了确定性程序。

### 9.2 核心流程（伪代码）

```text
trace = []
for step in 1..max_steps:
    decision = planner.next_action(task, trace, tools)   # {thought, action, action_input}
    if decision is None or decision.action in (None, "final"):
        answer = decision.action_input.answer or last_observation(trace)
        break
    result = tools.execute(decision.action, decision.action_input)
    trace.append(AgentStep(thought, action, action_input, result.output))
answer = answer or last_observation(trace)
success = bool(answer.strip())
```

任务成功率判定（`minillm/evaluation/agent_eval.py`）：

$$
\mathrm{Success}=\mathbb{1}\big[\text{answer}\neq\varnothing\big]\cdot
\mathbb{1}\big[\exists\,k\in\mathrm{keywords}:k\in\text{answer}\big]\cdot
\mathbb{1}\big[\mathrm{expected\_tools}\subseteq\mathrm{actual\_tools}\big]
$$

### 9.3 经典出处

* Yao et al., *ReAct: Synergizing Reasoning and Acting in Language Models*, ICLR 2023 —— ReAct 原始论文。
* Wei et al., *Chain-of-Thought Prompting Elicits Reasoning in Large Language Models*, NeurIPS 2022 —— 思维链。
* Schick et al., *Toolformer: Language Models Can Teach Themselves to Use Tools*, NeurIPS 2023 —— 工具学习。
* Anthropic, *Building Effective Agents*, 2024 —— 工程视角的 Agent 设计模式（workflow vs agent）。

### 9.4 本项目实现位置

| 组件 | 符号 | 说明 |
| --- | --- | --- |
| 工具基类 | `minillm/agent/tools.py` → `BaseTool` | `name/description/run(**kwargs) -> ToolResult`；失败返回 `ok=False` 不抛异常 |
| 安全计算器 | `CalculatorTool` | **绝不使用 `eval`**：先正则白名单，再用 `ast.parse` + 节点白名单 `_eval_ast` 递归求值；支持 `+ - * / %` 与括号，拒绝超长/超大结果 |
| 知识检索 | `KnowledgeSearchTool` | 依赖 `RAGPipeline.search`，输出 `[编号] doc_id / 标题（score=…）：snippet` |
| 文本统计 | `TextStatsTool` | 字符数 / 词数（英文按空格词、中文按单字）/ 行数 |
| 单位换算 | `UnitConvertTool` + `convert_units` / `parse_conversion_text` | 温度、长度、质量、时间四类；跨类别报错；支持自然语言解析 |
| 工具注册表 | `ToolRegistry` | `register/get/execute/describe`；`execute` 把未知工具、参数错误、内部异常都收敛成 `ToolResult(ok=False)` |
| 工具工厂 | `TOOL_FACTORY` / `build_tools` | 按 `cfg.agent.tools` 装配；缺 RAG 时跳过 `knowledge_search` 并告警 |
| 规划器接口 | `minillm/agent/planner.py` → `BasePlanner` | `next_action(task, steps, tools) -> dict \| None` |
| 规则规划器 | `RuleBasedPlanner` | 意图优先级 `calculator → unit_convert → text_stats → knowledge_search`；已执行过的工具不重复调用（防死循环）；最后把 observation 压成一句答案 |
| LLM 规划器 | `LLMPlanner` | 让 TinyGPT 输出 JSON 动作，`json.JSONDecoder().raw_decode` 解析；失败返回 `None` 由上层兜底 |
| 执行循环 | `minillm/agent/react.py` → `ReActAgent.run` | 记录完整 `AgentTrace`；规划器异常→兜底 final；步数耗尽→取最后 observation |
| 评估 | `minillm/evaluation/agent_eval.py` → `evaluate_agent` | 成功率 / 平均步数 / 平均延迟 / 逐任务 details |

### 9.5 关键超参与工程取舍

* **规则规划器是「必做」，LLM 规划器是「可选」**：39 万参数的 TinyGPT 还不具备可靠的
  JSON 规划能力，所以默认 `cfg.agent.planner="rule"`。`build_planner` 在 `llm` 模式失败时
  自动回退到 `rule`，保证服务永远可用。
* **安全计算器用 AST 白名单**：这是本项目在 Agent 安全上最实质的工程点——
  `eval` 会直接执行 `__import__("os").system(...)`，而 AST 白名单只允许数字常量和四则运算。
* **工具异常不炸循环**：`ToolRegistry.execute` 把异常转成 observation 文本，
  规划器仍能继续决策，符合「Agent 要能容错」的工程直觉。
* **`max_steps=5`**：任务预期最多「检索 + 汇总」两步，5 步足够且能兜住异常循环。

## 10. FastAPI 与 pydantic v2

### 10.1 一句话直觉

> 用类型注解描述「请求长什么样、响应长什么样」，框架自动做校验、序列化和 OpenAPI 文档；
> 业务逻辑收在一个门面对象里，HTTP 层只负责翻译错误码。

### 10.2 关键机制

请求校验（pydantic v2）：

$$
\text{valid}(r)=\bigwedge_{f\in\mathrm{fields}}\mathrm{constraint}_f(r_f),
\qquad
\neg\text{valid}\Rightarrow \mathrm{HTTP}\ 422
$$

本项目对空白串统一拒绝（`_non_blank`）：`"   "` 在校验阶段直接 422，不进入检索/Agent。

### 10.3 经典出处

* FastAPI 官方文档：<https://fastapi.tiangolo.com/>
* pydantic v2 迁移指南：<https://docs.pydantic.dev/latest/migration/>
* OpenAPI Specification 3.1：<https://spec.openapis.org/oas/v3.1.0>

### 10.4 本项目实现位置

| 组件 | 符号 | 说明 |
| --- | --- | --- |
| 应用工厂 | `minillm/serving/app.py` → `create_app(cfg=None)` | `app.state.service` / `app.state.config` 暴露给测试；配置优先级：显式参数 > `MINILLM_CONFIG` 环境变量 > `configs/default.yaml` > 默认值 |
| 请求/响应模型 | `minillm/serving/schemas.py` | `SearchRequest`、`RagAnswerRequest`、`AgentRunRequest`、`GenerateRequest`、`ChatRequest` 等；`Field(min_length/max_length/ge/le)` 约束与 `field_validator` 空白校验 |
| 服务门面 | `minillm/serving/service.py` → `AppService` | `health/stats/rag_search/rag_answer/agent_run/generate/chat`；初始化失败降级为 `degraded` 而不是崩溃 |
| 端点 | `app.py` | `GET /health`、`GET /v1/stats`、`POST /v1/rag/search`、`POST /v1/rag/answer`、`POST /v1/agent/run`、`POST /v1/generate`、`POST /v1/chat` |
| 错误契约 | `_validation_handler` / `_http_handler` / `_unhandled_handler` | 统一 `{"error": {"type", "message"}}`；校验错误 422，RAG 不可用 503，未捕获异常 500 |
| 启动 | `python -m minillm serve` 或 `python -m minillm.serving.app` | uvicorn 参数来自 `cfg.serve` |

**健康/统计字段中的生成器取值**：`/health.generator` ∈
`model_guarded`（默认：TinyGPT + 守卫）/ `model`（未启用守卫）/ `extractive`（无模型回退）/
`unavailable`（RAG 流水线不可用）；`model_loaded` 会自动拆开 `GuardedGenerator` 包装判断。
注意 `/v1/generate` 是**裸模型生成演示，不经过守卫**；`/v1/rag/answer` 与 `/v1/chat` 的 RAG 路径才经过守卫。

### 10.5 关键设计取舍

* **Facade + 无状态方法**：`AppService` 内部不修改共享状态，方法可以安全被 FastAPI 并发调用，
  也便于单测直接 `AppService(cfg)` 后调用方法。
* **降级而非崩溃**：数据缺失时 `/health` 返回 `status="degraded"`，检索类接口返回 503 +
  具体原因；这样「没有训练产物的全新克隆」也能启动服务并演示降级路径。
* **pydantic v2 写法**：用 `field_validator` 而不是 v1 的 `validator`；
  错误处理器里把 `exc.errors()` 裁成 JSON 可序列化的 `{loc, msg, type}`，
  因为 pydantic v2 的 `ctx` 可能包含 `ValueError` 对象，直接返回会导致 500。
* **`/v1/chat` 的 auto 路由**：`_auto_mode` 用「是否含算式 / 单位 / 统计关键词」在
  Agent 与 RAG 之间选路，把「工具型任务」与「知识型任务」分开，是产品化时很常见的小设计。

## 13. 术语表

| 术语 | 含义（本项目语境） |
| --- | --- |
| TinyGPT | 自研 decoder-only 因果语言模型，同时充当 SFT 策略与奖励/价值网络 backbone |
| checkpoint `kind` | `gpt`（预训练/SFT）、`policy`（PPO 后策略）、`reward`（奖励模型）三种检查点类型，统一由 `minillm/models/checkpoint.py` 存取 |
| token 级 KL | 逐动作（逐 token）计算 `logπ_θ - logπ_ref`，作为奖励惩罚项 |
| GAE | 用 `γλ` 截断的指数加权优势估计，平衡偏差与方差 |
| 抽取式回退 | 没有模型检查点时，从检索片段里选最相关句子作为答案，并标注 `source="extractive"` |
| gold doc_id | RAG 评估中「正确答案所在父文档」的编号，召回按它判定 |
| `rag_hard` | 内置的 10 条人工语义改写难例评估结果，与 `rag`（简单集）形成对照 |
| `model_guarded` | `/health.generator` 取值：TinyGPT 已加载且外面包了生成质量守卫 |
| `extractive_fallback` | RAG 答案的 `source`：模型输出未通过守卫校验（或生成异常），答案改由抽取式生成器给出 |
| `missing_quantity` | 守卫规则：问题在问「几点/多少/电话/金额…」而答案不含任何数字时，判定为答非所问 |
| `best_step` | PPO 中 greedy 评估奖励最优的 step；0 表示 SFT 初始策略就是最优 |
| `mean_reward_final` | PPO 最后一步（不做最优挑选）的 greedy 评估奖励，用于透明记录退化 |
| chunk | 检索片段；FAQ 一条 = 一个 chunk，KB 一篇 = 一个 chunk |
| degraded | 服务启动了但 RAG 流水线不可用时的健康状态 |
| `tiny_cfg` | 测试用极小配置 fixture，把训练压到 1~3 步内完成 |
